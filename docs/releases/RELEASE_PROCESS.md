# Hermes Connector: обязательная процедура выпуска обновления

1. Проверить `git status` и актуальный `origin/main`. `VERSION`, `AssemblyInformationalVersion` и видимая GUI-версия должны совпадать с номером тега `vX.Y.Z`.
2. Запустить Windows и Linux тесты, тест криптографической проверки, swap/rollback. Выявленные дефекты классифицировать; отсутствие реального E2E **не** заменяется CI.
3. Проверить исходный EXE через доверенный Windows Defender. Hosted GitHub Actions иногда пишет `Scanning ... was skipped` и exit=0: **это не результат сканирования**. Проверять текст `found no threats`, код 0 и SHA256 **этого же** файла. В случае отсутствия проверки — блокировать выпуск.
4. Проверить Authenticode. Если подпись отсутствует, **не объявлять стабильный принятый выпуск**. Аварийный выпуск возможен только с отдельным решением владельца, пометкой GitHub `prerelease` и явным предупреждением.
5. Сначала создать GitHub **draft** с точным SHA коммита и `HermesBridge.exe`, удостовериться что GitHub API возвращает asset digest, затем опубликовать как `prerelease` или полноценный релиз по фактической приёмке.
6. Проверить без GitHub-токена: публичный `/repos/AQiX-space/hermes-bridge/releases`, флаг `draft=false`, `tag_name`, правильный `browser_download_url`, asset `digest=sha256:...`, скачанные байты.
7. Проверить на Windows **старую исполняемую логику обновлятора**: прежний `CurrentTag` выбирает новый выпуск, `StageAsync` загружает EXE с проверкой хеша. Отдельно проверять замену и rollback на невоспроизводящей пользовательские данные тестовой машине.
8. Не обновлять или отзывать активные рабочие сеансы без конкретного согласования. Реальный операторский Windows E2E и серверный отзыв живой SSH-сессии — отдельные критерии допуска в стабильную эксплуатацию.
9. Зафиксировать выпущенный tag, sha256, CI run, Defender evidence, статус GUI/E2E и блокеры. Ни одна сборка CI в одиночку не означает установленный Windows-продукт.
